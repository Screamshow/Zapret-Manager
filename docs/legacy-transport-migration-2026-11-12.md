# Existing Zapret installations: panel-only transport migration

ZMS 4.71.6 fixes the upgrade path for existing installations lacking a transport ownership receipt. Forkop X 2.7.3 and Xrust 0.0.40 remain unchanged. Update ZMS; recognized installations require no Zapret reinstall or strategy reset.

The installer records whether the **previous** backend has this fork's exact flavor and update-source contract. Only that upgrade path invokes migration after the new backend is installed. Fresh panel installation over an unknown installation does not automatically claim it.

For an installation without a receipt, migration requires a package-manager version, ownership of both the nfqws/nfqws2 executable and common/nft.sh by that package, and an exact component/format/version/binary/helper hash tuple. The offline allowlist covers 56 verified payload records (51 distinct identities): Zapret 72.20260307-r1 APK/IPK from remittor's published architecture archives, this fork's ARM r100 packages, and the pinned Routerich Zapret2 1.0.5.2-r15 APK source. Archive/package hashes and payload hashes are retained in `legacy-transport-payloads.json`. ZIPs were checked against GitHub release asset digests before extracting APK and IPK separately; their executable bytes differ. No downloads or package installation occur during migration.

Unknown or modified payloads, symlinked roots/files/state/receipts/backups, a different package owner and existing receipts are not automatically claimed or renewed. This also preserves a mismatched receipt after an external replacement instead of accepting the new binary. The hash list confirms a supported canonical payload; it cannot prove which historical installer originally installed byte-identical packages. Adoption is limited to an existing panel with this fork's contract, and does not change strategy or package contents apart from the explicitly supported nft producer helper.

The previous helper is backed up in the private transport-ownership directory. Pinned hashes are rechecked while creating the receipt; Forkop revalidates them before applying its guard. The existing Forkop `prepare` operation updates the producer and active queues without a Zapret/core restart. Failed prepare makes the panel update return an error, retains the receipt for retry and does not print successful installation. It does not silently classify an unsupported installation as protected.

Verification:

- Shell syntax, panel-contract, backend-behavior, proxy-transport, legacy-transport and LuCI/Web render tests passed. Added tests exercise all pins, APK/IPK ownership, changed binary/helper/version, symlinked binary/receipt/backup, preservation of existing invalid receipts and prepare error propagation.
- Existing OpenWrt 25 x86/64 VMware VM: exact legacy APK installed **only in an isolated package root**, with synthetic dependency providers; the live VM package database was unchanged. Production migration functions and the released Forkop guard ran against that root in an owned network namespace. Receipt/helper migration and repeated prepare passed. Real UDP payload with SO_MARK 0x0a000000 bypassed the NFQUEUE counter, while SO_MARK 0x08000000 Direct payload was delivered and incremented it. Host nft rules, configuration hashes and installed packages matched before/after. No new VM was created.
- Operator MT6000 192.168.90.1: full panel installer upgraded the real existing 4.71.5 panel and Zapret 72.20260307-r1 APK. Receipt was created; all four existing queue rules received packet/connection-mark exclusions. Forkop/Zapret UCI, core binaries, package inventory and sing-box/nfqws PIDs matched. DNS and HTTPS passed. Private snapshots and exact helper/nft rollback remain only on the router under `/root/zms-4716-migration-20261112`.

Limits: IPK migration control flow is covered by shell fixtures and canonical extracted payloads; a full OpenWrt 24 panel upgrade was not executed. No customer router was accessed. Queue isolation was tested with real marked UDP in a namespace, not a new AWG throughput/camouflage benchmark. Unknown historical package revisions remain intentionally unadopted.
